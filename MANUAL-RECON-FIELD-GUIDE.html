Front matter

How to use this guide

Read it once end to end. After that it is a lookup: each phase is self-contained, and the checklist on the last page is what you will actually use on the second engagement onwards.

What this is

A manual methodology. Every command here you type yourself, on a Kali box, with tools that cost nothing and need no account. Nothing in this guide depends on our automation — that exists (see the appendix) and it is faster, but a tool you cannot reproduce by hand is a tool you cannot debug, extend or defend in a report.

What it is not

It is not an exploitation manual. It stops where recon stops: you will finish with an inventory, a fingerprint per host, a set of verified leads and a ranked list of what to attack and why. Turning a lead into a finding is the next document.

Chapter 1

How results lie to you

This chapter is first because every later command depends on it. The failure mode of recon is not missing a host. It is believing a result your tool could never have produced correctly — and clean output looks identical either way.

The one rule

Rule

An absence is only evidence if your instrument could have shown you the presence.

Before you write "no SPF record", "no subdomains", "that endpoint does not exist" or "the port is closed", answer one question: if the thing were there, would this exact command have shown it to me? If you cannot answer yes, you have not got a negative result. You have got no result.

The practical form of that rule is a baseline: before you believe what a server says about a thing that exists, find out what it says about a thing that cannot possibly exist.

Baseline a web server before you believe any path

$ curl -s -o /dev/null -w "%{http_code} %{size_download}B %{content_type}\n" \
    https://ginandjuice.shop/recon-baseline-$RANDOM$RANDOM

Anything that invented path returns is what the server returns for everything. A 200 means content discovery on that host is meaningless until you account for it. A 403 means the same in the other direction.

The live example: the baseline that was taken at the wrong place

Four invented paths on the same host, same command, same minute:

/recon-baseline-41398257        404   7350B   text/html; charset=utf-8
/catalog/recon-baseline-17724   404   7368B   text/html; charset=utf-8
/api/recon-baseline-90031       404   7350B   text/html; charset=utf-8
/my-account/recon-baseline-5512 200   7506B   text/html; charset=utf-8

captured: ginandjuice.shop, 24 Nov 2026

Trap — a catch-all scoped to a mount point

The host answers an honest 404 at the root, and 200 for anything under /my-account/. If you baseline once at / and then fuzz /my-account/, every single word in your wordlist comes back as a discovered endpoint. Hundreds of findings, all of them the same page.

So: baseline per directory, not per host. One probe at the root tells you about the root. This is not a rare configuration — any SPA or app mounted on a subpath does it, and it cost us real false positives in our own tooling the week this guide was written.

The six ways a recon result goes wrong

1. Your resolver is blind

A hardcoded public resolver that cannot be reached returns nothing, and nothing is indistinguishable from "the record does not exist".

$ # prove the resolver answers for THIS domain before trusting any negative
$ dig +short NS portswigger.net @1.1.1.1
$ # empty? the resolver is the problem, not the domain. Fall back:
$ grep nameserver /etc/resolv.conf
Trap

On a corporate network, outbound UDP/53 to 1.1.1.1 and 8.8.8.8 is frequently blocked. Every DNS query times out, your notes record "no SPF, no DMARC, no MX" for a domain that has all three, and the only symptom is that the step took 80 seconds instead of two.

Positive control: query a record you know exists — the apex NS — and only proceed when it comes back.

2. Wildcard DNS makes every name resolve

$ dig +short this-name-cannot-exist-9183.example.com
$ # and to tell NXDOMAIN apart from a dead resolver, which +short cannot:
$ dig +noall +comments this-name-cannot-exist-9183.example.com \
    | grep -o 'status: [A-Z]*'

If the first returns an address, the zone has a wildcard and your 4,000-name permutation list will "resolve" in full. Resolve a few random names first; subtract the wildcard answer from every result.

3. A wildcard certificate makes certificate logs useless

$ openssl s_client -connect ginandjuice.shop:443 ... | openssl x509 -ext subjectAltName
X509v3 Subject Alternative Name:
    DNS:ginandjuice.shop, DNS:*.ginandjuice.shop

captured: ginandjuice.shop, 24 Nov 2026

Trap

Certificate transparency for ginandjuice.shop returns exactly two names: the apex and the wildcard. That is not evidence the site has no subdomains — it is evidence they bought one certificate that covers all of them. A wildcard converts your best passive source into a source that structurally cannot help, and it says so only if you look at the certificate.

4. A dead or throttled source returns a silent zero

crt.sh             44 names
certspotter        59 names
hackertarget       38 names
rapiddns            9 names
subdomain.center  176 names
otx              HTTP 429  — 0 names
wayback-cdx         4 names

captured: seven keyless sources, portswigger.net, 24 Nov 2026

That 429 is the interesting line. Had the script printed only counts, OTX would have read as "nothing there". Always surface the HTTP status of every source, and treat a non-200 as untested, never as empty.

5. Rate limiting arrives as HTTP 200

Plenty of stacks answer a throttled request with 200 OK and a body saying "too many requests". If you are only looking at status codes you will read a wall of successes. Check bodies and response times, not just codes.

6. Something between you and the target forges answers

Some middleboxes and consumer routers answer SYN on selected ports for any destination, including addresses that cannot be routed. The cure is a canary: scan an address reserved for documentation, which can never answer.

$ # 192.0.2.1 is TEST-NET-1 (RFC 5737). Nothing is there. Ever.
$ nmap -Pn -p 22,80,443,2000,5060,8080 192.0.2.1

Whatever port list you intend to scan the target with, canary that exact list. A canary over six ports tells you nothing about the other 994 you are about to scan, and 2000 and 5060 belong in every list — those are the two this network forges.

Any port that reports open on that address is being forged by your own network path. Subtract those ports from every scan result for the rest of the engagement, and write down which ones they were.

What you should have now
  • A resolver you have proved answers for this domain.
  • A note of whether the zone has wildcard DNS.
  • A canary result listing any ports your network path forges.
  • The habit of baselining per directory before believing a path.
Chapter 2  passive

Define the target

Ten minutes that stop you spending a day on the wrong estate. You are establishing what the apex is, who registered it, who runs its DNS, and which networks it occupies.

Registration, via RDAP not whois

$ curl -sL https://rdap.org/domain/portswigger.net | jq '{
    handle, status,
    registrar: [.entities[]? | select(.roles[]?=="registrar") | .vcardArray[1][][]? ]
      | map(select(type=="string")) | unique,
    events: [.events[]? | {(.eventAction): .eventDate}]
  }'

RDAP is JSON, so it is greppable and scriptable; whois output format varies per registry and will break your parsing. rdap.org redirects to the authoritative server for the TLD, so one URL works everywhere.

What you want from it: creation date (a domain registered three weeks ago that looks like the client's brand is a phishing domain, not an asset), expiry, status codes such as clientTransferProhibited, and the registrar.

Nameservers tell you who to ask and who they trust

$ dig +short NS portswigger.net
ns-573.awsdns-07.net
ns-1337.awsdns-39.org
ns-1955.awsdns-52.co.uk
ns-194.awsdns-24.com

captured: portswigger.net, 24 Nov 2026

Route 53, and deliberately spread across four TLDs so that one TLD outage cannot take the zone offline. That tells you the DNS is professionally run, and it tells you where a zone transfer attempt would go.

Always try the zone transfer. It takes four seconds.

$ for ns in $(dig +short NS portswigger.net); do
      dig +noall +answer AXFR portswigger.net @$ns | head -5
  done

It will almost always fail. When it does not, you have the entire zone in one request and the rest of chapter 3 is unnecessary.

Which networks does it live on

$ dig +short A portswigger.net | while read ip; do
      echo -n "$ip  "
      curl -s "https://rdap.org/ip/$ip" | jq -r '"\(.name)  \(.country)  \(.handle)"'
  done

Group hosts by the network they sit in. A host on the client's own allocation is theirs to defend; a host on a cloud provider's shared range may be a managed service where the finding belongs to the provider. This grouping is also how you spot the origin server hiding behind a CDN — one host in a different ASN to all the others is almost always the real backend.

Scope, at the only point it matters

You now have a list of networks. Check each one against the engagement scope before chapter 5 starts sending requests. Shared cloud ranges and third-party SaaS hosts are the two things that get people in trouble, and both appear in an asset list that looks entirely like the client's.

What you should have now
  • The apex, its registration dates and status.
  • The authoritative nameservers, and a zone-transfer attempt on each.
  • Apex addresses mapped to networks and countries.
  • A scope decision per network, made before you sent any traffic.
Chapter 3  passive keyless

Passive asset discovery

Every query in this chapter goes to a third-party aggregator, never to the target. You can run all of it before authorisation lands, and the target sees nothing. It is also where most people stop too early — they run one source and move on.

Certificate transparency

Every publicly trusted certificate is logged. Those logs are searchable, and a certificate is issued for a hostname, so the logs are a hostname index.

$ # crt.sh - returns JSON, one object per certificate
$ curl -s 'https://crt.sh/?q=%25.portswigger.net&output=json' \
    | jq -r '.[].name_value' | tr '\n' ' ' | tr ' ' '\n' \
    | sed 's/^\*\.//' | grep -i portswigger.net | sort -u
$ # certspotter - second CT source, different index, no key for modest volume
$ curl -s 'https://api.certspotter.com/v1/issuances?domain=portswigger.net&include_subdomains=true&expand=dns_names' \
    | jq -r '.[].dns_names[]' | sed 's/^\*\.//' | sort -u
Trap — crt.sh caps the query inside the database

Large domains hit an internal row limit and which rows survive is effectively arbitrary. If your result is a suspiciously round number near ten thousand, you have a sample, not the history. Narrow the query (per subdomain, or by date) and run it repeatedly rather than trusting one pull.

Separately: a wildcard certificate means CT knows only *.example.com. See chapter 1 — an empty CT result is sometimes a statement about the certificate, not the estate.

Passive DNS and scraped indexes

$ curl -s 'https://api.hackertarget.com/hostsearch/?q=portswigger.net'   # host,ip CSV
$ curl -s 'https://api.subdomain.center/?domain=portswigger.net' | jq -r '.[]'
$ curl -s 'https://rapiddns.io/subdomain/portswigger.net?full=1' \
    | grep -oP '(?<=>)[a-z0-9_.\-]+\.portswigger\.net(?=<)' | sort -u
$ curl -s 'https://otx.alienvault.com/api/v1/indicators/domain/portswigger.net/passive_dns' \
    | jq -r '.passive_dns[].hostname' | sort -u

Web archives — URLs, not just hostnames

$ curl -s 'https://web.archive.org/cdx/search/cdx?url=*.portswigger.net/*&output=text&fl=original&collapse=urlkey&limit=20000' \
    | tee urls-archive.txt \
    | awk -F/ '{print $3}' | sort -u >> raw-names.txt

The archive is the only source here that gives you paths. Keep the full URL list; chapter 7 uses it as a wordlist that is specific to this target, which beats any generic list.

Write them down — every later chapter reads these files

Nothing above redirects to a file. Add | tee -a raw-names.txt to each source command, then build the one file the rest of the guide consumes:

$ # one directory per engagement
$ export D=portswigger.net; mkdir -p ~/eng/$D && cd ~/eng/$D
$ # one bare hostname per line, in-domain only, sorted
$ tr '[:upper:]' '[:lower:]' < raw-names.txt \
    | sed 's/^[*][.]//; s/[.]$//' \
    | grep -E "(^|[.])${D//./[.]}$" \
    | sort -u > names-all.txt
$ wc -l names-all.txt
Trap — one column, or the next chapter breaks

names-all.txt must be bare hostnames, one per line, sorted. Keep the which-source-said-what mapping in a separate file. Put two columns in this one and dnsx -l reads the annotation as part of the hostname, while comm — which requires sorted input and says nothing when it does not get it — silently reports every name as new.

$ sort -u raw-names-with-source.txt > names-sources.tsv

Now the part nobody measures: how much of it is real

Resolve every name you collected, with a wildcard control first.

$ # control: if an impossible name resolves, the zone is a wildcard and
$ # the numbers below are meaningless
$ # +short prints answer data only, so NXDOMAIN and "resolver timed out"
$ # both print NOTHING. Read the status field instead.
$ dig +noall +comments this-cannot-exist-7741923.portswigger.net \
    | grep -o 'status: [A-Z]*'
$ # then resolve the set - A, AAAA and CNAME. An -a-only query
$ # counts AAAA-only and CNAME-only names as if they were dead.
$ dnsx -l names-all.txt -silent -a -aaaa -cname -resp -retry 2 -o resolved.txt
$ awk '{print $1}' resolved.txt | sort -u > names-live.txt
$ comm -23 names-all.txt names-live.txt > vhost-candidates.txt
$ wc -l names-all.txt names-live.txt vhost-candidates.txt

Trap — what this table is not

These are one domain, on one day, with n=22 in the top bucket. Treat the shape as the finding — corroboration predicts reality — not the exact percentages, and re-measure on your own target rather than quoting these. If you resolve with -a alone, every AAAA-only and CNAME-only name lands in the "does not resolve" bucket and the hit rates are wrong.

What this means in practice

Corroboration is a quality signal. A name four sources agree on is real, every time. A name one source alone reports is live about one time in twelve. That is how you triage 188 names into a morning's work instead of a week's.

Spot-checking the single-source names shows why: alongside auth.portswigger.net (real, four sources) sit authu, authv, adminq, awsg, aie, burpcollaborator1e — single-character mutations of real names, all NXDOMAIN, all from one source. That source has high recall and low precision: it is guessing, and it is worth running precisely because it guesses, as long as you never report its output as an asset without resolving it.

Trap — do not delete the 140

The obvious move is to drop every NXDOMAIN name. Do not. A name in a certificate log that does not resolve is the definition of a virtual-host candidate or an internal-only host — the certificate proves somebody provisioned it. Eleven of the single-source names did resolve, too. Keep them in a vhost-candidates.txt and revisit them in chapter 7; just never call them assets.

What you should have now
  • names-all.txt — the union, with which sources reported each.
  • names-live.txt — the subset that resolves, wildcard-controlled.
  • vhost-candidates.txt — the ones that do not, kept deliberately.
  • urls-archive.txt — target-specific paths for later.
  • A note of every source that errored, marked untested rather than empty.
Chapter 4  active keyless

Resolution and DNS structure

You now touch the target's DNS, though not its web servers. The goal is to turn a name list into a structured picture: which names are live, what they point at, and which of those pointers are dangling.

Resolve, keeping the record type

$ dnsx -l names-all.txt -silent -a -aaaa -cname -resp -o resolved.txt
$ # or without Go tools, one name at a time:
$ # one qtype per invocation: `dig ... A AAAA CNAME` does NOT query all
$ # three - the last one wins, and you conclude there is no A record.
$ for t in A AAAA CNAME; do dig +noall +answer auth.portswigger.net $t; done
Trap — A-only queries hide v6-only hosts

The default in most pipelines is an A lookup. A host with only an AAAA record is then classified as dead. Query both. If you have no working IPv6 path from your box, record those hosts as untested — not as down, and not as up.

Follow every CNAME to its end

$ dig +short CNAME status.example.com
$ # chase the whole chain, which can be three or four hops
$ dig +trace +nodnssec status.example.com | tail -20

Where the chain ends matters more than where it starts. A CNAME into a cloud provider that no longer has the resource behind it is a subdomain takeover: you register the resource, and the target's hostname serves your content.

$ # the three-part test for a takeover candidate
$ dig +short CNAME sub.target.com          # 1. points at a third party?
$ dig +short A $(dig +short CNAME sub.target.com)   # 2. target dead?
$ curl -is https://sub.target.com | head -30   # 3. provider error page?

All three must hold. The provider's "no such bucket / no such app / domain not configured" page is the confirmation; a CNAME alone is not.

Trap — NS delegation takeover leaves no record to find

If a subzone is delegated to nameservers that no longer host it, querying NS sub.target.com through a recursive resolver returns SERVFAIL and nothing to inspect. You have to ask the parent directly, without recursion:

$ dig +norecurse NS sub.target.com @$(dig +short NS target.com | head -1)

This class is rated the highest-impact takeover variant and almost no tool reports it, because the recursive answer looks like a plain failure.

Permutation, only once you have a wildcard answer

$ # build a label list from what you already found, then permute
$ cut -d. -f1 names-live.txt | sort -u > labels.txt
$ for l in $(cat labels.txt); do
      for env in dev staging uat test qa sandbox preview internal admin; do
        echo "$l-$env.target.com"; echo "$env-$l.target.com"
      done
  done | sort -u > permutations.txt

Permutation against a wildcard zone produces thousands of "live" hosts and teaches you nothing. Run the wildcard control from chapter 1 first; if the zone wildcards, skip this entirely and say so in your notes.

What you should have now
  • Each live name with its address family and full CNAME chain.
  • A takeover candidate list where all three conditions were checked.
  • A parent-side delegation check on any subzone that SERVFAILs.
  • Hosts grouped by address — one IP serving forty names is one target.
Chapter 5  active keyless

HTTP probing and fingerprinting

First contact with the application. You want, per host: does it answer, on which schemes, what is it, which version, and what does the response leak for free.

Probe both schemes, keep the redirect chain

$ httpx -l names-live.txt -silent -sc -title -tech-detect -server \
    -location -cl -ip -o http-probe.txt
$ # by hand, and what you should actually read:
$ curl -sSi https://ginandjuice.shop/ | head -20
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 10487
Connection: close
Set-Cookie: session=jKPPeHNnYbzZH3Zg6doMiA8R0MwXflMP; Path=/; Secure; HttpOnly; SameSite=None
X-Backend: b691dfa1-d265-40de-bc58-96dda3ad4c4c
X-Frame-Options: SAMEORIGIN

captured: ginandjuice.shop, 24 Nov 2026

Three things in seven lines:

  • X-Backend is a backend instance identifier. Collect it across many requests — it tells you how many backends there are, whether the load balancer is sticky, and gives you a way to tell which instance answered when behaviour differs between requests.
  • SameSite=None on the session cookie means the browser will send it on cross-site requests. That is a prerequisite for CSRF, and it is a deliberate choice someone made.
  • What is absent: no Strict-Transport-Security, no Content-Security-Policy, no X-Content-Type-Options. Absence here is safe to assert — you have the full header block in front of you, so your instrument could have shown the presence.

Version numbers: read the filenames, not the fingerprinter

An automated fingerprint of that homepage returns:

tech: ["React", "Angular"]        versions: {}

Which is true and nearly useless. The script tags say considerably more:

/resources/js/react.development.js             200   109,909 B
/resources/js/react-dom.development.js         200 1,077,021 B
/resources/js/angular_1-7-7.js                 200   195,161 B
/resources/js/subscribeNow.js                   200     3,739 B
/resources/footer/js/scanme.js                  200     6,307 B

captured: ginandjuice.shop, 24 Nov 2026

Two findings the fingerprinter missed
  • React development builds in production. The .development.js bundles ship verbose errors, component names and internal warnings, and they are roughly ten times the size of the production build. That is both an information leak and a performance defect, and it is visible in the filename.
  • AngularJS 1.7.7. AngularJS went end-of-life in January 2022 — no further security patches exist. A pinned, EOL, client-side framework is a dependency finding on its own, and AngularJS specifically brings client-side template injection into scope wherever user input reaches an interpolated expression.

So: always list the script sources and read them. A version in a filename or a query string is the cheapest fingerprint you will ever get.

$ curl -s https://ginandjuice.shop/ \
    | grep -oP '(?<=src=")[^"]+' | sort -u

Methods and CORS, in two requests

$ curl -s -o /dev/null -D - -X OPTIONS https://ginandjuice.shop/ | head -5
$ curl -s -o /dev/null -D - -H 'Origin: https://recon-probe.example' \
    https://ginandjuice.shop/ | grep -i access-control
HTTP/1.1 405 Method Not Allowed
Allow: GET

(no Access-Control-* headers returned)

captured: ginandjuice.shop, 24 Nov 2026

Allow: GET from a 405 is a free method inventory. When you do find a permissive CORS policy, check whether it reflects arbitrary origins and whether Access-Control-Allow-Credentials is set — a wildcard origin without credentials is usually inert.

What you should have now
  • Status, title, server, redirect target and content length per host.
  • The complete response header block for each interesting host, saved raw.
  • A technology list with versions, taken from filenames and paths.
  • Allowed methods, and a CORS reflection test per API-looking host.

Read it as four separate signals

FieldWhat it tells you
subjectAltNameEvery name this certificate covers. On shared infrastructure a SAN list routinely contains dozens of unrelated hostnames — and those are the other tenants, which are not your scope.
issuerThe CA, and by extension the platform. Amazon-issued certificates mean ACM, which means the host sits behind an AWS load balancer or CloudFront, which tells you the origin is elsewhere.
notAfterExpiry. A certificate expiring in days on a production host is an availability finding. Long-past-expiry on a host that still answers suggests something nobody is watching.
wildcardA *. entry explains a thin CT result (chapter 1) and means the operator can stand up new hostnames without appearing in any log at all.

Harvest SANs across every live host

        | openssl x509 -noout -ext subjectAltName 2>/dev/null \

  done < names-live.txt | sed 's/^\*\.//' | sort -u > san-names.txt

That final comm is the point of the exercise: it prints hostnames no passive source gave you. Feed them back into chapter 4 and resolve them.

Trap — the SAN list is not the client's asset list

On a shared load balancer or a multi-tenant platform, the certificate covers every tenant on that listener. Harvesting SANs will hand you other companies' hostnames that sit in the same cloud account as your target. They look like discoveries. Resolve them, check who they belong to, and keep only the ones inside the engagement's scope.

Lazy chunks: the filenames that exist as no string

In a webpack build, the admin bundle's URL is not written anywhere. The runtime assembles it from two object literals:

A crawler only ever loads the chunks the pages it visited demanded, so the admin and settings chunks are never fetched. Rebuild them by hand:

$ curl -s https://target.com/static/js/runtime.js > rt.js
$ # the two maps: id->name and id->hash
$ grep -oP '\{[0-9]+:"[^"]*"(,[0-9]+:"[^"]*")*\}' rt.js
$ # and the publicPath they are relative to - NOT the runtime's own directory
$ grep -oP '\.p\s*=\s*"[^"]*"' rt.js
Trap — publicPath, not the bundle's directory

Chunk prefixes resolve against webpack's publicPath, which defaults to the site root. Joining them to the directory the runtime happens to live in produces /static/js/static/js/… and a page of 404s. If your minted URLs all 404 while the app works fine, this is why.

Secrets, and how not to invent them

Vendor-prefix patterns like those are high-confidence: the prefix is the evidence. Name-based searching is where it goes wrong.

Trap — a key NAME is not a key VALUE

Searching for api_key, client_secret or password followed by a quoted string finds this, constantly:

Ze().getItem("client_secret"),i=Ze().getItem("acme_base_url")
{path:"/forgot_password.php",name:"forgot-password"}
e[e.Password=Ye(13)]="Password"
accessToken:"example-AP-accessToken"
apiKey:"no-api-key"

Storage key names, route names, enum labels, i18n strings, placeholder defaults. Every one of them matches a naive name-and-quoted-value pattern, and in our own tooling this exact class produced twelve false findings including two rated critical.

CheckWhat to do
the qualifier-all hard fail, ~all soft fail, ?all or +all no protection at all. +all is a finding on its own.
10-lookup limitCount every include, a, mx, ptr, exists and redirect, recursively — RFC 7208 §4.6.4 puts the limit on the whole evaluation, not on one record. Past ten, evaluation returns PermError. PermError is not a pass: RFC 7208 §8.7 says it "gives no true indication about the authorized use", and receivers may reject (SHOULD use 550) or deliver with annotation — behaviour is local policy and varies. $ # recursive lookup count - the thing nobody checks
$ # counts every lookup-consuming term, recursively, with a depth guard.
$ # an include loop would otherwise recurse until the shell dies.
$ spf_count() {
      local d=$1 depth=${2:-0} n=0 rec inc
      [ "$depth" -ge 5 ] && { echo 0; return; }
      rec=$(dig +short TXT "$d" | tr -d '"' | grep -m1 '^v=spf1')
      for t in $rec; do
        case "${t#[+~?-]}" in
          include:*|redirect=*) n=$((n+1));;
          a|mx|ptr|a:*|mx:*|ptr:*|exists:*) n=$((n+1));;
        esac
      done
      for inc in $(echo "$rec" | grep -oP '(?:include:|redirect=)\K\S+'); do
        n=$((n+$(spf_count "$inc" $((depth+1)))))
      done
      echo $n
  }

Trap — DMARC is only read from _dmarc

A DMARC record published at the apex is ignored by every receiver. Only _dmarc.<domain> is consulted. So the real policy here is p=quarantine, and the apex copy is a leftover.

Now consider a tool that greps the domain's TXT records for v=DMARC1 — a very common shortcut. It finds the apex record first and reports p=none: no DMARC enforcement, a medium-severity finding, completely wrong. Query the exact name, never grep the apex.

Other DMARC detail that matters: sp= is the subdomain policy and is often weaker than p=; pct= below 100 means the policy applies to a sample only; a missing rua= means nobody is receiving reports, so nobody would notice abuse.

Chapter 13  active keyless

Authenticated recon

Everything so far was outside the login. The expensive bugs are inside it — broken access control and object-level authorisation are consistently the highest-paying classes in the industry, and none of them are visible to an unauthenticated scan. What you can do here depends entirely on what access you were given, so start by taking inventory of that.

First: get the session into your terminal

Log in with a browser, then move the credential to the command line. Three ways, in order of preference:

$ # 1. intercepting proxy - the only one that shows you the whole flow
$ # first run only: start it, browse to http://mitm.it through the proxy
$ # and install the CA certificate, or every HTTPS page will fail.
$ mitmproxy --mode regular --listen-port 8080 -w flows.mitm
$ #    browse the app through it, then read every request it made
$ mitmdump -nr flows.mitm -s '/dev/stdin' <<'EOF'
  def response(f): print(f.request.method, f.request.pretty_url)
EOF

$ # 2. copy the request out of devtools as curl, then strip it down
$ #    Network tab -> right click -> Copy as cURL

$ # 3. keep the cookie jar in a file and reuse it
$ # never put a real password on the command line: it lands in
$ # your shell history and in the process list, readable by others.
$ read -rs -p 'password: ' PW; echo
$ curl -s -c jar.txt -b jar.txt \n    --data-urlencode "username=$USERNAME" \n    --data-urlencode "password=$PW" https://target.com/login
$ curl -s -b jar.txt https://target.com/my-account
Trap — two credentials, not one

Modern apps carry a session cookie and a bearer token, often with different lifetimes and different authorisation logic. A request that works in the browser and fails from curl is usually missing the second one — a CSRF header, an Authorization bearer, a tenant header. Diff your curl request against the browser's until they match, then start removing headers one at a time to learn which actually matter. That exercise is itself a finding generator.

Then: inventory your access, and branch

Trap — the role matrix logs itself out

If /logout is in endpoints.txt, the loop below requests it, destroys the session, and every remaining row for that role comes back 401 — which reads exactly like "this role has no access to anything". The grep -v above drops the obvious ones; check your own list before running a matrix across it.

The four-cell matrix — the only authz test that proves anything

For any endpoint that takes an object identifier, you need four requests. Three of them are controls, and skipping them is how false findings get reported.

#RequestExpectedWhat it proves
1Victim's session → victim's object 200The object exists and the endpoint works.
2Attacker's session → attacker's own object 200Your session is valid and you have permission to the function. Without this, a 403 in test 3 means nothing.
3Attacker's session → victim's object 403If this returns 200, that is the finding.
4No session → victim's object 401Separates broken object authorisation from no authentication at all.
Trap — read the next command correctly

A body comparison is a weak oracle: signed URLs, nonces and timestamps make two identical records differ, and a cached error page makes two different records match. Use it to raise a lead, never to close one. And note how it reads: diff printing nothing means the two bodies are identical, i.e. the attacker received the victim's record — silence is the finding, not the all-clear.

The strong oracle is a state change you can observe from the other side: make the change as the attacker, then log in as the victim and look. That is the only version that survives review.

$ # weak oracle: compare bodies. Empty diff = SAME = the finding.
$ curl -s -b attacker.txt "https://target.com/api/invoice/4471" | tee /tmp/a.json
$ curl -s -b victim.txt   "https://target.com/api/invoice/4471" | diff - /tmp/a.json
Trap — three ways an authz test lies
  • Request your own object first. A 403 on someone else's object proves nothing if you also get 403 on your own — you simply lack the function permission. This is the single most common false negative.
  • A flag in the response body is not a decision. can_read: true in a JSON payload is a default the server sent you, not proof the server enforced anything. Verify by logging in as the object's owner and seeing whether the change you made is there.
  • Editing a response in your proxy changes nothing. Intercepting a response and flipping "isAdmin":false to true alters what your browser renders. It does not alter the server. Confirm against the real endpoint with a fresh request.

Role diffing

$ # capture the full endpoint set per role, then diff them
$ for role in admin manager user readonly; do
      while read ep; do
        printf '%s\t%s\t' "$role" "$ep"
        curl -s -b "jar-$role.txt" -o /dev/null -w '%{http_code}\n' "https://target.com$ep"
      done < endpoints.txt
  done | tee role-matrix.tsv
$ awk -F'\t' '$3==200 {print $2}' role-matrix.tsv | sort | uniq -c | sort -n

An endpoint that returns 200 for every role is either public by design or missing function-level authorisation entirely. The matrix tells you which endpoints to read the code for — and it is reusable as a regression test after the client fixes something.

Before you send a state-changing request

Write the restore request first. If a test creates, modifies or deletes something, you must be able to put it back, and the restore request belongs in your notes next to the test request. Clean up after yourself in the same session — not next week, when you have forgotten what the original value was.

What you should have now
  • A working session in the terminal, with every header it genuinely needs.
  • The authenticated endpoint set, diffed against the unauthenticated one.
  • A role matrix across every account you were given.
  • Object identifiers classified, with the sequential ones tested through all four cells.
  • A restore request recorded for everything you changed, and executed.

Capture requests raw, not as prose

Every finding's reproduction steps should be a request someone can paste into a terminal or a proxy and send, unmodified. Not a description of a request.

$ # --trace-ascii gives you the exact bytes sent and received
$ curl -s --trace-ascii raw/invoice-4471-attacker.txt \
    -b attacker.txt "https://target.com/api/invoice/4471"
$ # and send untrusted values as literals, never as fields curl may interpret
$ curl --form-string "comment=@not-a-file" https://target.com/api/comment
What every lead file needs
  • The baseline you compared against, with the command that produced it.
  • All four requests of the matrix, raw, including the controls that passed.
  • The timestamp and the host that answered (the X-Backend-style header, if there is one — behaviour differing between backends is a real phenomenon).
  • The restore request, if anything changed.
  • A one-line statement of what would make you withdraw the finding.

That last item is the one people skip and the one that saves you. Writing "this is invalid if the endpoint turns out to be public by design" forces you to go and check whether it is.

Record untested, not just found

Your notes need a section for things you could not test and why: a source that returned 429, a host that blanket-403s so path results mean nothing in either direction, an IPv6-only host you had no route to, a cap that fired. Without it, the next person reads your clean result as coverage you never had.

Chapter 15

Knowing when to stop

Recon expands without limit. The skill is deciding which of two hundred leads deserve the next hour, and saying out loud which ones you abandoned.

Rank by what the lead would cost an attacker

TierLeadWhy it ranks here
1Pre-authentication surface on a host nobody owns — forgotten subdomains, dangling CNAMEs, staging environments, exposed admin panels. No credentials needed, and nobody is watching. Highest impact per unit of effort for both of you.
2Sequential object identifiers on an authenticated endpoint.If authorisation is missing anywhere, this is the cheapest way to prove it, and it is the industry's highest-paying bug class.
3Verified credentials or keys in client-side code. Direct access, but verify validity before reporting — most are rotated, sandboxed or public by design.
4Version-based leads: EOL frameworks, known-vulnerable components.Real, but needs exact version matching and usually a reachable code path. Easy to over-claim.
5Posture findings: missing headers, weak SPF, no DNSSEC. True, cheap, and they belong in the report — but they are not why you were hired.

Kill a lead properly

A dead lead should be dead for a stated reason, written down. Three legitimate reasons:

  • Disproved. You ran the test with working controls and the behaviour is correct. Record the controls.
  • Out of scope. The host belongs to a third party. Record who, and move on without probing further.
  • Untestable with what you have. Needs a second account, an authenticated session, an out-of-band collaborator, a route you do not have. This is not the same as disproved, and it must not be filed as one.
Trap — the thing that looks like completion

"I ran the tools and found nothing" is the sentence to be most suspicious of. Before you write it, go back through chapter 1: did your resolver answer? did the canary come back clean? did you baseline per directory? did every source return 200? was your detector capable of showing a positive on a target you know has one?

If you cannot answer all of those, you have not found nothing. You have not looked.

Hand over

What the next person needs from you, in one page: the live host list ranked, the untested list with reasons, the credentials and jars you used, the baselines you measured per host, and the single sentence you would start with tomorrow morning.
